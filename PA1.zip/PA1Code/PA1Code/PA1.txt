
Task 1: 

the program does not meet the "final balance= initial balance" requirement because balance
is updated by multiple threads (concurrently) using a non-atomic read-modify-write (in both methods deposit and withdraw)

 
bugs: 
	-Missing mutual exclusion: The depositor and withdrawer on the same Account can interleave their updates, 
		causing lost updates.
	-No visibility guarantee: Without synchronization, 
		a thread may not see/read the most recent value written by another thread (stale reads).

fix: 
	-guard all balance access with a per-account lock
	-make the methods deposit, withdraw and getBalance and toString synchronized
		or wrap the updates in synchronized(lock){} block 
	-keep the existing join() calls so the printing happens after all threads finish.

Task 2:


	* The actual order in which threads begin running is decided by the 
			JVM/OS scheduler (CPU availability, load, JVM/OS policies, and only loosely influenced by priority). 
			Calling `t.start()` just requests execution; 
			it does not guarantee when that thread runs.
	
	* Therefore, changing the start order cannot ensure consistency. 
			The inconsistency comes from a data race /non-atomic updates to balance, 
			which can occur regardless of who starts first.
	* To preserve consistency must add synchronization around the `balance` updates; start order alone is not a correctness mechanism.
	
Task 3:

	+ shared state is 'balance' aka account.balance

		- Account.getBalance()

			double b;					// critical (read for visibility)
			b = balance;

	Task 6 --> 
		both approaches ensure correctness regarding to to 
		mutual exclusion and visibility
			Task 4: 
				Locks the entire method on the account instance (this)
				
				pros--> * Simple/safe: one keyword, hard to miss a path. 
						* Readable: intent is obvious at the method boundary. 
						* Low overhead per call: a single lock/unlock.
						* Less chance of misuse: always locks on this (predictable).
				
				cons--> * locks the entire method, including non-critical work.
						* Longer lock hold time: other threads may wait more --> more contention.
						
						
			Task 5:
				Locks only the minimal critical section 'balance' 
				via private lock object
				
				pros--> * lock only the minimal critical section (e.g., balance update).
						* Shorter lock hold time: can reduce waiting and improve throughput-> more operation per second. 
						* use a private lock for better encapsulation and flexibility (better encapsulation than locking on this).
				
				cons--> * Easier to misuse: risk of locking the wrong object or missing a code path.
						* More boilerplate: extra code and potentially more lock/unlock boundaries.
						* Consistency required: every access must use the same lock.
